# Skill and AGENTS.md Writing Guide

## 1. 触发

| DO | DON'T |
|---|---|
| 创建、重写或审查 `SKILL.md` 时加载本 guide | 只做普通代码修改时加载本 guide |
| 创建或审查仓库根目录/模块目录 `AGENTS.md` 时加载本 guide | 把本 guide 当作项目业务规范或代码审查规范 |
| 先判定文档类型，再使用 §2 或 §3 的标准 | 用 SKILL.md 标准直接套 AGENTS.md，或反过来 |

**判定表**

| 文档 | 读者/加载方式 | 目标 | 规范章节 |
|---|---|---|---|
| `AGENTS.md` | 项目 agent，每次进入作用域可见 | 正确编码、测试、部署 | §2 |
| `SKILL.md` | agent 按触发条件按需加载 | 触发后立即执行可复现流程 | §3 |

## 2. AGENTS.md 规范

AGENTS.md 面向项目级配置。主文件只放所有分支都需要的执行规则；背景、长示例和分支细节放模块级 `AGENTS.md` 或有明确触发条件的参考文档。

### 2.1 DO/DON'T

| DO | DON'T |
|---|---|
| 将主文件控制在 100–150 行，并把分支细节下沉到子目录或引用文件 | 把架构百科、历史叙述和所有模块细节塞进根文件 |
| 用决策表先说明技术选型、适用条件和验收证据 | 用长段落让 agent 自己猜选择条件 |
| 把部署/发布写成编号步骤，每步给出命令和完成条件 | 只写“部署后验证”而没有可执行检查 |
| 写领域规则的目标行为，并配一条对应 DON'T | 连续堆叠 15 条以上 DON'T 而没有 DO |
| 放 3–10 行真实生产代码或命令，标明文件/入口 | 使用伪代码、占位符或脱离仓库的抽象示例 |
| 说明模块边界、依赖方向和改动后的验证入口 | 用“全局都可改”“自行决定”掩盖边界 |
| 每条规则只保留一个权威来源，并链接细节 | 在根文件、README、子文档重复同一规则 |

### 2.2 决策表模板

| 情况/证据 | 选择 | 执行动作 | 完成条件 |
|---|---|---|---|
| <可观察条件> | <技术/模块 A> | `<命令或入口>` | <可检查结果> |
| <另一条件> | <技术/模块 B> | `<命令或入口>` | <可检查结果> |
| 无法判定 | 先收集证据 | `<读取/检查命令>` | <证据足够或明确阻塞> |

### 2.3 程序化工作流

1. **定位**：读取根规则、模块边界和构建入口。完成条件：知道目标模块、允许改动范围和验证命令。
2. **选择**：按决策表选择实现路径。完成条件：记录选择及对应证据。
3. **实现**：只改目标模块，复用现有接口和代码模式。完成条件：调用方、错误路径和配置变更均已处理。
4. **验证**：运行最小相关测试、构建或 smoke 命令。完成条件：命令成功且结果覆盖改动路径。
5. **交付**：列出文件、行为变化、验证结果和未解决项。完成条件：读者可复现验证。

### 2.4 AGENTS.md 自检清单

| 检查项 | DO（通过标准） | DON'T（失败信号） |
|---|---|---|
| 范围 | 根文件 100–150 行；细节有指针 | 根文件超过 150 行且没有拆分理由 |
| 选型 | 每个分支有证据、动作、验收 | 只有偏好，没有适用条件 |
| 工作流 | 步骤编号且每步有完成条件 | “完成后检查”之类不可执行语句 |
| 规则 | 每条 DON'T 有配对 DO | 连续禁令导致 agent 不敢行动 |
| 示例 | 3–10 行真实代码/命令且可定位 | `foo()`、`<path>` 等伪示例充当证据 |
| 边界 | 模块所有权和依赖方向明确 | 修改范围依赖猜测 |
| 披露 | 参考文件可通过指针按分支加载 | 孤立 `_docs/` 无触发指针 |

## 3. SKILL.md 规范

SKILL.md 面向可复用能力。它的正文应让 agent 在触发后直接执行，不把背景知识和执行步骤混成一团；长协议、案例和完整命令参考应放在引用文件。

### 3.1 DO/DON'T

| DO | DON'T |
|---|---|
| frontmatter 用一句话写清触发分支和不触发边界 | 使用“相关任务”“需要时”等模糊触发条件 |
| 先写触发/不触发，再写编号执行流程 | 让 agent 读完长背景才知道是否应加载 |
| 用 DO/DON'T 表配对行为、安全红线和替代动作 | 只写“禁止/严禁/不得”而不提供下一步 |
| 每个步骤包含命令、输入、输出和完成条件 | 用“适当处理”“验证一下”等不可执行步骤 |
| 用决策表消除 role、模式、平台或错误分类歧义 | 在多个章节用互相冲突的散文规则解释选择 |
| 保留 3–10 行真实命令/代码作为最小可运行示例 | 只给概念描述或无法运行的伪命令 |
| 主文件聚焦执行；把协议字段、历史案例推送到引用文件 | 为了“完整”把主文件写成百科 |
| 输出格式写出必需字段、证据和阻塞状态 | 只要求“总结结果”而没有交付契约 |
| 对外部 skill 用明确路径交叉引用，并说明何时读取 | 写“见相关文档”但不给路径或触发条件 |

### 3.2 决策表模板

| 触发证据/状态 | DO：选择的流程 | DON'T：排除的流程 | 验收证据 |
|---|---|---|---|
| <用户词/文件/平台> | <步骤组或命令> | <不适用路径> | <输出/状态/文件> |
| <错误或边界状态> | <恢复/上报动作> | <危险降级动作> | <可核对结果> |
| 证据不足 | <补证据步骤> | <猜测或静默降级> | <明确 BLOCKED/待确认> |

### 3.3 编号工作流与输出

1. **确认触发**：核对用户请求、环境和权限。完成条件：满足触发条件且不触发排除项。
2. **准备输入**：读取最小必要文件/状态，记录关键 ID、路径或版本。完成条件：输入清单完整。
3. **执行主流程**：按决策表运行命令；每一步记录结果。完成条件：主动作产生预期状态或明确失败。
4. **验证交付**：用独立证据核对结果，不把日志提示当作完成信号。完成条件：验收字段齐全。
5. **输出**：按固定格式报告结论、改动/产物、证据、阻塞和下一步。完成条件：用户可复核且无未标注推测。

### 3.4 SKILL.md 自检清单

| 检查项 | DO（通过标准） | DON'T（失败信号） |
|---|---|---|
| 触发 | description 和正文各有明确触发/不触发 | 任何相似任务都可能误触发 |
| 长度 | 主文件约 100–150 行，细节有指针 | 主文件承载全部协议和案例 |
| 流程 | 连续编号；每步有完成条件 | 章节跳号、步骤依赖隐含 |
| 决策 | 行动前有场景→动作→验收表 | 关键选择散落在多段文字 |
| 配对 | 每个 DON'T 有对应 DO/替代 | 连续禁令或只写风险 |
| 示例 | 至少一个 3–10 行真实片段 | 只有抽象建议 |
| 安全 | 红线、替代和上报状态明确 | 失败时静默重试/降级 |
| 输出 | 字段、证据、BLOCKED 语义固定 | 输出标准依赖临场发挥 |

## 4. 共同原则

| 有效模式（DO） | 失败模式（DON'T） |
|---|---|
| 渐进式披露：主文件只保留所有分支必需内容，细节由指针按需加载 | 过度探索：把架构概述、历史和所有警告塞入主文件，造成无关上下文 |
| 程序化工作流：编号动作并为每步写完成条件 | 步骤不可执行：只有目标，没有命令、路径或验收 |
| 决策表：在行动前按证据选择路径 | 长段规则：让 agent 自行推断模式和优先级 |
| 真实示例：引用仓库中可运行的 3–10 行代码/命令 | 抽象示例：伪代码无法验证，也无法复用 |
| 领域特定规则：少量、具体、能改变行为的规则 | 无差别堆叠几十条规则，信号被噪声淹没 |
| DO/DON'T 配对：每条红线给出正确动作和验收 | 连续 DON'T 无 DO，导致 agent 过度保守 |
| 模块化：一个文件一个职责，按分支/序列拆分 | 新模式破坏旧文档：旧 REST/轮询规则覆盖新 WebSocket 路径 |

## 5. 坏→好对比示例

### 示例 1：触发条件

**坏：** `处理相关的项目任务时使用。`

**好：** `触发：用户要求读取 OpenCode 历史、提到 opencode.db 或 ~/.local/share/opencode。不触发：普通代码修改。`

### 示例 2：禁止规则

**坏：** `禁止直接修改状态文件。`

**好：**

| DO | DON'T |
|---|---|
| 使用 `mailbox status --state IDLE` 写状态，并读取 `status.json` 验证五字段 | 直接编辑 `status.json`，或把文件存在当作进程存活证明 |

### 示例 3：不可执行流程

**坏：** `完成部署后检查服务是否正常。`

**好：**

```bash
1. ./scripts/deploy.sh staging
2. curl -fsS http://127.0.0.1:8080/health
3. ./scripts/smoke.sh staging
```
完成条件：health 返回 200，smoke 命令退出码为 0，并记录部署版本。

## 6. 质量评分标准

按 1–10 分逐项评分；总分为六项平均值，低于 7 分需修改。

| 维度 | 9–10 分 | 6–8 分 | 1–5 分 |
|---|---|---|---|
| 触发与边界 | 触发分支、排除项和依赖均可判定 | 大部分明确，少数模糊 | 无触发条件或经常误触发 |
| 结构与披露 | 100–150 行核心，细节按分支指向 | 略长或拆分不均 | 大量背景混入执行路径 |
| 可执行流程 | 编号步骤、命令、输入、完成条件齐全 | 有步骤但验收不完整 | 主要是抽象叙述 |
| 决策与规则 | 决策表覆盖歧义；DO/DON'T 成对 | 有表但覆盖不全 | 规则冲突或连续禁令 |
| 示例与领域性 | 真实 3–10 行示例，规则具体有效 | 示例或领域规则偏弱 | 无真实示例、全是泛化建议 |
| 输出与维护 | 固定输出、交叉引用、单一事实源 | 可交付但引用/维护一般 | 无输出契约或内容重复过时 |

**审查结论格式：** `文档类型｜总分｜是否拆分｜Top 3 问题｜最小修改路径｜验证证据`。
